# JOMUL project-asset work

The user's goal is a reusable sketch → CAD → 3D → photo skill. The documents in `docs/make-skill/` are design records, not proof that a generator consumes a rule. `docs/`, `.poc/`, and `poc/` are intentionally excluded from Git; do not mistake an untracked artifact for a committed implementation.

For skill work, use `skills/ceramic-cad-to-3d/scripts/run.py --workspace <project-root>`. Read the skill's `selection.json` and `references/pipeline.md` for the active selection; its `assets/accepted-profile.json` is the canonical generation profile. All selected runtime code is inside the skill. The repository `scripts/jomul-project-assets.py` is a compatibility shim. `scripts/jomul-build.py` and `docs/artifacts` are historical development/comparison tools, not alternate skill generation paths.

Run the skill entrypoint's `preflight` before generation and `preflight --release` before claiming a finished page. Every ordinary invocation checks the runtime lock. After an intentional implementation change, review selection coverage, refresh it with `tests/update_lock.py --write` and run the affected regression tests. Never refresh a lock just to conceal an unexpected change. Preserve selected moon/bowl reference outputs and compare the same viewport/scroll points when presentation changes.

The current CAD contract is technical-dense for single and multiple projects. Multiple parts share one sheet. Isometric guide rings come from the CAD profile, never a generic bowl icon. CAD labels are English except the user's clay/glaze names. The last gallery has no visible title/caption or later section; it uses the accepted photo frame and pointer profile. Prefer shared source code and profile input to re-creating a similar-looking implementation. If a component is not shared yet, state that limitation; do not report a documented rule as implemented.

For changes to shape, material, motion, or gallery behavior, preserve unaffected approved assets, work in a separate comparison target, and compare the same viewport/scroll points. Do not use an approximate manual rollback: restore the exact previous code/assets or state that the snapshot is unavailable. Record adopted feedback in the stage's generation rule first, then add regression coverage. The chess fixture is reserved for final evaluation, not intermediate tuning.

Keep page implementation on `feat/main-page-design` (integrated through `feat/main`) and skill implementation on `feat/make-skill`. Do not force-add local planning or PoC folders. A local merge is not evidence of a remote push; verify remote branch hashes before reporting synchronization.
