# Ceramic CAD to 3D

Read the [pipeline and decision status](references/pipeline.md) before starting or extending a project. This is a living skill: move adopted decisions into its active profile and consuming generator with a meaningful output check; keep rejected experiments out of the active path. The documented 00–11 pipeline is the target workflow, while the commands below are the currently supported subset. Do not infer implementation from a checklist or a passing PoC alone.

Use a Python environment with [requirements.txt](requirements.txt) installed for P1 `--intake`/`--answer`; existing manual CAD commands can use `python3`. Resolve `scripts/run.py` relative to this skill and pass `--workspace /path/to/project` for `new`, `resume`, `revise`, `verify`, and `rollback`. Read [input contract](references/input.md) before preparing a P1 intake, answer, or manual CAD config. The entrypoint stores each project under `.poc/jomul-project-assets-workspaces/<NN>-<slug>/` with a state file and review log; snapshots are separate per project.

For `new --intake`, inspect the sketch itself and create a reviewed P1 extraction with source regions, uncertainty, shape features, and questions. For each rotational part, also provide a reviewed outer profile. The CLI checks the source sketch hash, stores the P1 extraction and question state in the project, adds missing exact-dimension and clay/glaze questions, and reports pending fields in `intake/summary.json`. Ask only those unresolved questions. Save each real user reply with its message reference and verbatim text as an answer JSON; call `resume --answer` for one or more replies. If the answered dimensions require a corrected silhouette, supply a separately reviewed `resume --profile PART=FILE` update. The CLI validates answer IDs, ranges, fields, and evidence, then assembles dimension/material/config JSON and builds CAD when all CAD-blocking fields and dimensions are available. Preserve exact ranges as ranges until the user selects a value. Never label a sketch observation or illustrative shrinkage as a manufacturing confirmation. A P1 extraction is agent-reviewed input; this CLI does not interpret image pixels independently. The old `new/resume --config` path remains for already reviewed manual CAD inputs. `resume` without new input reports the pending state. A P1 project cannot silently replace derived CAD with a manual config. Correcting an already confirmed answer needs a reviewed intake revision; do not overwrite its original evidence. `revise` records feedback and snapshots the project before replacing CAD inputs; `verify` checks source and output hashes plus the CAD geometry contract; `rollback` restores a named project snapshot without touching another project.

A `handled-vessel` P1 intake may omit the P2 profile: it preserves questions and real answers and can be verified while CAD is blocked. Keep handle and body under one part; never route the body alone through rotational CAD as the complete mug. Attach a separately reviewed body `resume --profile PART=FILE` and [handle path](references/handled-vessel.md) `resume --handle PART=FILE`; these are hashed in P1 without clearing unanswered CAD questions. Once all blocking fields have real answers, the P1 route assembles the same handled config and builds it. A manual `--config` uses that same renderer for a separate provisional comparison workspace and cannot overwrite a P1 project. If the user authorizes provisional handle depth or section, archive the verbatim reply as a deferred P1 answer and continue in the isolated manual comparison workspace; do not label the provisional numbers user-confirmed. Inspect the GLB from the side and rear before accepting a smooth handle, because numeric front placement and valid fusion do not prove a smooth join. For photo-backed smooth C handles, use the shared shape-preserving path in the handle contract for CAD and STEP, check that the sampled lower path does not reverse or dip below its attachment, and use CAD-sourced 3D guide lines for the browser wire stage; raw GLB tessellation edges are not the intended wire drawing. With build123d, a handled config produces a CAD guide plus one joined STEP/GLB solid. The solid path checks joint volume, open cavity, STEP reimport, GLB bounds, and numeric front-view placement against the sheet. The one-sheet technical SVG supports one or two parts in desktop, mobile, and mobile-short layouts; short landscape reuses desktop. Each sheet has part-specific `frontBox` metadata for later CAD-to-wire placement. Keep the user-selected visual reference in `assets/accepted-profile.json`; the selected fixture hashes protect the moon and bowl examples only. New projects must derive their own sheet and `frontBox` from their inputs.

For a CAD-ready single `handled-vessel` with a verified GLB, `motion-preview PROJECT --motion FILE` builds a local CAD→wire→clay axis-motion review. The motion JSON must contain `schemaVersion: 1`, `status` (`reviewed-provisional` or `user-confirmed`), provenance, `tiltDirection`, `tiltDegrees`, `bodySpinDegrees`, and `axisPrecessionDegrees`; see [motion input contract](references/input.md#motion-input). The command reads `motion.axisRig` from the accepted design profile, uses the shared axis component and the project’s own CAD/GLB, then runs the four-viewport browser gate before recording a preview. `verify` checks the preview and browser report hashes; a CAD rebuild invalidates the old preview. Docker, cached Puppeteer Chrome and Vite are required for this gate. This is a motion review stage, not a full project page; rotational GLB generation, multi-part page assembly, glaze and the final-photo handoff within that preview are still unsupported.

Report the current state honestly. Unsupervised image-to-P1 extraction and reviewed profile creation, unreviewed handle extraction, general asymmetric or three-plus-part CAD, STEP/GLB for ordinary rotational inputs, full 3D scene, complete-page gallery assembly, and publication remain outside this executor. Record these as unsupported rather than substituting a rotational shape or presenting a CAD sheet as a complete project page. When adding the full project-page stage, read `page` from `assets/accepted-profile.json` as a generation input: fill the first viewport with the largest fully contained CAD sheet; emit no visible page header, assumption badge, stage title/detail, progress line, or footer. Keep CAD-internal dimensions, material and provenance notes, plus nonvisible accessibility labels. Apply this to single and multiple projects, and verify the generated DOM and desktop/mobile screenshots so an old scene template cannot reintroduce copy. The current bowl viewer copies implement and test this page rule; the v0 CLI does not assemble a full page yet.

When a full project-page renderer is added, use the accepted moon page axis hierarchy and the axis-motion decision in [selection.json](selection.json): the vessel and its CAD-sourced wire turn together around the vessel axis while that tilted axis changes azimuth through 360°. Camera-only 180° orbit belongs to side/rear shape inspection, not the project motion. The moon right 14° and 390° body turn are comparison values until the new project’s direction, angle, and pacing are reviewed. Verify the handle stays in frame at intermediate angles on desktop and mobile. This v0 executor still does not build that page.

The executable selection and exclusions are in [selection.json](selection.json); the single active profile is [assets/accepted-profile.json](assets/accepted-profile.json). Every invocation checks the packaged runtime lock before changing project state. Historical PoC dispatchers and viewers are outside this execution path. Selected baseline HTML/JS under assets/baselines are immutable verification evidence, not alternate page renderers.

Use the same entrypoint for `preflight`, `shrinkage --input SPEC.json`, and `gallery PROJECT --photos FILE`. The gallery command builds a final-gallery component with verified roles, source hashes and EXIF-free images: zero photos, one hero, or the selected actual-hero plus smaller process-photo pair. Other photo combinations require explicit scatter review input (2–8 photos and a stable seed); otherwise they stop with `MULTI_PHOTO_LAYOUT_PENDING`. Scatter remains a visual candidate; do not substitute it for the selected pair or revive the equal-grid experiment. See the [photo input](references/input.md#gallery-input). The background/glaze/framing modules are preserved and component-tested; their integration into an approved general full page remains pending. `page` and `preflight --release` stop until that work is complete.

Run `python3 /path/to/ceramic-cad-to-3d/scripts/run.py --workspace /path/to/project preflight` for package integrity. Run the skill's `tests/test_runtime.py` with requirements installed to verify copied-package execution, selected single/multiple CAD output, exact rollback, gallery rules and handled solids. Browser motion requires a Vite server for the workspace, Three.js, Docker/Puppeteer and its Chrome cache. Do not claim complete page parity from package or component checks.

For maintenance, update the existing selection entry and consumer together, review the diff, refresh the lock with `python3 tests/update_lock.py --write` from the skill directory, and run affected tests. Do not add another PoC viewer as a fallback or silently refresh a drifted lock.

Use `status PROJECT [--changed cad|motion|gallery]` to inspect current stage readiness and downstream impact without mutating the workspace. Read the execution-state contract in [pipeline](references/pipeline.md#execution-state-contract). Gallery preparation can run before CAD is ready.

Before applying reviewed CAD changes, `status PROJECT --config FILE` shows the selective rebuild plan. `resume/revise --config` uses that plan; legacy projects rebuild once to record fingerprints. After CAD changes, previously reviewed motion is automatically rebuilt and browser-gated. A failed motion job preserves CAD and input; `resume PROJECT` retries once. Projects without reviewed motion input still require `motion-preview --motion FILE`.

For decision-linked behavioral verification, run `check-decisions [--output REPORT.json]` with the skill Python dependencies and Node available. It executes the suites linked in `selection.json` and records their scope, logs and source hashes. `passed-within-scope` is not full-page approval. Browser motion and gallery checks remain separately executed evidence; see [verification scope](references/pipeline.md#decision-linked-verification).
