# JOMUL project assets

Read the [pipeline and decision status](references/pipeline.md) and [current verification status](references/verification-status.md) before starting or extending a project. This is a living skill: move adopted decisions into its active profile and consuming generator with a meaningful output check; keep rejected experiments out of the active path. The documented 00–11 pipeline is the target workflow, while the commands below are the currently supported subset. Do not infer implementation from a checklist or a passing PoC alone.

Use a Python environment with [requirements.txt](requirements.txt) installed for P1 `--intake`/`--answer`; existing manual CAD commands can use `python3`. Run `scripts/jomul-project-assets.py` from this repository for `new`, `resume`, `revise`, `verify`, and `rollback`. Read [input contract](references/input.md) before preparing a P1 intake, answer, or manual CAD config. The entrypoint stores each project under `.poc/jomul-project-assets-workspaces/<NN>-<slug>/` with a state file and review log; snapshots are separate per project.

For `new --intake`, inspect the sketch itself and create a reviewed P1 extraction with source regions, uncertainty, shape features, and questions. For each rotational part, also provide a reviewed outer profile. The CLI checks the source sketch hash, stores the P1 extraction and question state in the project, adds missing exact-dimension and clay/glaze questions, and reports pending fields in `intake/summary.json`. Ask only those unresolved questions. Save each real user reply with its message reference and verbatim text as an answer JSON; call `resume --answer` for one or more replies. If the answered dimensions require a corrected silhouette, supply a separately reviewed `resume --profile PART=FILE` update. The CLI validates answer IDs, ranges, fields, and evidence, then assembles dimension/material/config JSON and builds CAD when all CAD-blocking fields and dimensions are available. Preserve exact ranges as ranges until the user selects a value. Never label a sketch observation or illustrative shrinkage as a manufacturing confirmation. A P1 extraction is agent-reviewed input; this CLI does not interpret image pixels independently. The old `new/resume --config` path remains for already reviewed manual CAD inputs. `resume` without new input reports the pending state. A P1 project cannot silently replace derived CAD with a manual config. Correcting an already confirmed answer needs a reviewed intake revision; do not overwrite its original evidence. `revise` records feedback and snapshots the project before replacing CAD inputs; `verify` checks source and output hashes plus the CAD geometry contract; `rollback` restores a named project snapshot without touching another project.

A `handled-vessel` P1 intake may omit the P2 profile: it preserves questions and real answers and can be verified while CAD is blocked. Keep handle and body under one part; never route the body alone through rotational CAD as the complete mug. Attach a separately reviewed body `resume --profile PART=FILE` and [handle path](references/handled-vessel.md) `resume --handle PART=FILE`; these are hashed in P1 without clearing unanswered CAD questions. Once all blocking fields have real answers, the P1 route assembles the same handled config and builds it. A manual `--config` uses that same renderer for a separate provisional comparison workspace and cannot overwrite a P1 project. If the user authorizes provisional handle depth or section, archive the verbatim reply as a deferred P1 answer and continue in the isolated manual comparison workspace; do not label the provisional numbers user-confirmed. Inspect the GLB from the side and rear before accepting a smooth handle, because numeric front placement and valid fusion do not prove a smooth join. For photo-backed smooth C handles, use the shared shape-preserving path in the handle contract for CAD and STEP, check that the sampled lower path does not reverse or dip below its attachment, and use CAD-sourced 3D guide lines for the browser wire stage; raw GLB tessellation edges are not the intended wire drawing. With build123d, a handled config produces a CAD guide plus one joined STEP/GLB solid. The solid path checks joint volume, open cavity, STEP reimport, GLB bounds, and numeric front-view placement against the sheet. The one-sheet technical SVG supports one or two parts in desktop, mobile, and mobile-short layouts; short landscape reuses desktop. Each sheet has part-specific `frontBox` metadata for later CAD-to-wire placement. Keep the user-selected visual reference in `scripts/jomul-design-profile.json`; the selected fixture hashes protect the moon and bowl examples only. New projects must derive their own sheet and `frontBox` from their inputs.

For a CAD-ready single `handled-vessel` with a verified GLB, `motion-preview PROJECT --motion FILE` builds a local CAD→wire→clay axis-motion review. The motion JSON must contain `schemaVersion: 1`, `status` (`reviewed-provisional` or `user-confirmed`), provenance, `tiltDirection`, `tiltDegrees`, `bodySpinDegrees`, and `axisPrecessionDegrees`; see [motion input example](../../docs/artifacts/axis-motion-shared-study/mug-motion.json). The command reads `motion.axisRig` from the accepted design profile, uses the shared axis component and the project’s own CAD/GLB, then runs the four-viewport browser gate before recording a preview. `verify` checks the preview and browser report hashes; a CAD rebuild invalidates the old preview. Docker, cached Puppeteer Chrome and Vite are required for this gate. This is a motion review stage, not a full project page; rotational GLB generation, multi-part page assembly, glaze and final photos are still unsupported.

Report the current state honestly. Unsupervised image-to-P1 extraction and reviewed profile creation, unreviewed handle extraction, general asymmetric or three-plus-part CAD, STEP/GLB for ordinary rotational inputs, full 3D scene, photo gallery assembly, and publication remain outside this executor. Record these as unsupported rather than substituting a rotational shape or presenting a CAD sheet as a complete project page. When adding the full project-page stage, read `page` from `scripts/jomul-design-profile.json` as a generation input: fill the first viewport with the largest fully contained CAD sheet; emit no visible page header, assumption badge, stage title/detail, progress line, or footer. Keep CAD-internal dimensions, material and provenance notes, plus nonvisible accessibility labels. Apply this to single and multiple projects, and verify the generated DOM and desktop/mobile screenshots so an old scene template cannot reintroduce copy. The current bowl viewer copies implement and test this page rule; the v0 CLI does not assemble a full page yet.

The full-page study's single moon fixture must consume `motion.singleFraming` from the accepted design profile. That profile pins the approved moon JS as its source and requires transformed GLB-bound camera fitting plus a viewport-specific minimum wire-stage screen height. The browser gate must stop publication when the old fixed-distance `study-only-no-zoom` scene makes the moon too small. The size correction passed 16 assembled cases; do not call the common page visually equivalent to the approved moon until motion, light, material, and gallery framing are compared at matched scroll points. The multi-photo grid remains an unapproved candidate; the user's asymmetric, varied-size reference belongs to the next layout comparison.

The registered `gallery-cardinality-study` is a gallery-stage technical PoC for 0/1/3 photos. Its [generation record](../../docs/make-skill/08-scroll-page/100-gallery-cardinality-stage.md) and `docs/artifacts/page-components/gallery_markup.py` keep the zero-photo omission and reviewed photo metadata separate from the accepted one-photo gallery styling. The three-photo grid remains a visual candidate; its fixture deliberately repeats one actual photo. Do not present this stage as a complete page or as validation of three distinct final photos. The full renderer must supply verified photo roles and hashes, keep the gallery in the final viewport only, and test the 3D exit and reverse scroll on the assembled single/multiple page.

An isolated [full-page assembly PoC](../../docs/make-skill/08-scroll-page/101-full-page-assembly-poc.md) now uses one renderer for reviewed moon single and bowl multiple assets with zero, one, or three photos. Run its registered `full-page-study` build when changing the gallery or scene assembly; the gate checks four viewports and six points per case, reverse scroll, photo roles, full-sheet CAD, and transformed mesh framing. This PoC reads existing validated assets through the configured publisher and does not make this skill CLI capable of creating a new finished project page. Before exposing it through the CLI, connect project state and verified output hashes to the same renderer, keep the approved moon/bowl pages as baselines, and compare the new pages visually at matching scroll points. The multi-photo grid and page-wide look are still review candidates.

When a full project-page renderer is added, use the accepted moon page axis hierarchy and the [08 motion gap record](../../docs/make-skill/08-scroll-page/97-mug-axis-rotation-gap.md): the vessel and its CAD-sourced wire turn together around the vessel axis while that tilted axis changes azimuth through 360°. Camera-only 180° orbit belongs to side/rear shape inspection, not the project motion. The moon right 14° and 390° body turn are comparison values until the new project’s direction, angle, and pacing are reviewed. Verify the handle stays in frame at intermediate angles on desktop and mobile. This v0 executor still does not build that page.

For the provisional mug review, the user-shared `/.poc/mug-provisional-handoff-study/` URL must run the axis-motion viewer. Camera-only 180° side/rear inspection lives at `/.poc/mug-shape-inspection-study/`. Rebuild the registered current URL and its browser gate after a motion fix; a separate comparison URL alone does not update what the user is viewing.

Before modifying renderer or page code, follow the repository `AGENTS.md`, including preflight and preserved page baselines. The live approved pages and selected comparison artifacts must stay available for review.
